# Settings that can't change after the first apply

Several inputs and hardcoded values pick an Azure resource's shape once, at
create time. Changing them later forces Azure or the `azurerm` provider to
recreate the resource (data loss, downtime, or both) or is rejected outright.
Plan or price around these before the first `terraform apply`, not after.

| Setting | Module input | Effect of changing later | What to do instead |
| --- | --- | --- | --- |
| AKS availability zones (per node pool) | `aks_availability_zones` (`aks.tf`) | Azure treats a node pool's zone set as fixed at create time; changing it forces AzureRM to recreate the pool (or the whole cluster, for the default pool), draining every workload on it. | Pick the final zone set before the first apply. To add zone coverage later, add a new `azurerm_kubernetes_cluster_node_pool` instead of editing the existing pool's zones. |
| AKS network plugin, network policy, and `service_cidr` | Hardcoded: Azure CNI, no network policy engine, `service_cidr = 172.16.0.0/16`, `dns_service_ip = 172.16.0.10` (`aks.tf`) | Not caller-tunable. The Kubernetes Service CIDR is fixed for the life of the cluster; changing it means recreating the cluster. The range must not overlap any network the pods need to reach. | Confirm `172.16.0.0/16` is free before the first apply. A caller who needs a different plugin, policy engine, or CIDR brings their own cluster via `create_aks = false` (see [`docs/customer-managed-infrastructure.md`](./customer-managed-infrastructure.md)). |
| AKS subnet size | `aks_subnet_id` | Not a module setting, but sizing the referenced subnet too small is a build-time decision you cannot undo without moving the cluster to a new subnet. Azure CNI consumes one VNet IP per pod, not per node. | Size the subnet for max nodes x max pods per node, plus the extra nodes `aks_node_upgrade_max_surge` and any `temporary_name_for_rotation` pool rotation need during upgrades. |
| PostgreSQL networking | Fixed: VNet integration via `postgres_subnet_id`, a private DNS zone, and `public_network_access_enabled = false` (`database.tf`) | This module has no private-endpoint mode for PostgreSQL; it always attaches through a delegated subnet. Moving an existing server to a different connectivity model is not an in-place change: it requires a new Flexible Server and a restore. | Decide connectivity before the first apply. To point n8n at a server you manage with a different networking mode, use `create_database = false` and supply `postgres_external_*`. |
| PostgreSQL zone-redundant HA placement | `pg_primary_zone`, `pg_standby_zone`, `pg_enable_high_availability` | Azure only allows swapping the primary and standby zones as part of an HA failover, never through a plain `terraform apply` (`zone` and `high_availability[0].standby_availability_zone` are in `lifecycle.ignore_changes`, `database.tf`). | Treat a zone move as an out-of-band failover operation, not a Terraform change. Leave both zone inputs `null` to let Azure pick unless you have a specific placement requirement. |
| PostgreSQL geo-redundant backup | `pg_geo_redundant_backup_enabled` | Can only be set at server creation. Flipping it on an existing server forces a new server and a snapshot/restore. | Decide before the first apply. Enabling it later means provisioning a replacement server and restoring into it. |
| Redis high availability and clustering policy | `redis_high_availability_enabled`; clustering policy is always `NoCluster` (`redis.tf`) | Both are ForceNew on `azurerm_managed_redis` — Azure destroys and recreates the instance to change either one, dropping in-flight Bull jobs and breaking multi-main leader election until reconnect. | See [`docs/redis.md`](./redis.md#changing-high-availability-or-the-clustering-policy) for the drain procedure before flipping `redis_high_availability_enabled` on a live deployment. |
| Blob storage account replication | `storage_account_replication_type` (`storage.tf`) | Some conversions apply in place (for example LRS to GRS). Converting to or from a zone-redundant type (ZRS, GZRS, RAGZRS) is not always a live conversion in every region and can require a new storage account and a data migration. Check current Azure documentation for your region and source/target pair before changing it on an existing account. | Pick the final replication type up front for a production deployment. If a migration turns out to be required, provision a new storage account, copy the container's contents, and cut n8n over via `azure_blob_endpoint`/`existing_blob_*`. |
| AKS node OS disk size | `aks_node_os_disk_size_gb` | Changing it on an existing pool rotates the pool through `temporary_name_for_rotation`: nodes are recreated, and this is not a graceful cordon-and-drain. See [`docs/troubleshooting.md`](./troubleshooting.md#changing-aks_node_os_disk_size_gb-on-an-existing-cluster-disrupts-workloads). | Set the final disk size before the first apply, or treat a later change as its own maintenance window. |
| n8n encryption key | `n8n_encryption_key`, `n8n_encryption_key_secret_ref`, the `n8n_encryption_key` output | Not Azure-enforced, but changing the effective key makes every credential already stored in n8n's PostgreSQL database permanently unreadable. | Back up the generated key immediately after the first apply (`terraform output -raw n8n_encryption_key`) — see [`docs/post-deployment.md`](./post-deployment.md#capture-the-n8n-encryption-key). Never edit `n8n_encryption_key` on a deployment with existing data unless you are intentionally restoring that data's original key. |

This list covers module-level and Azure-level constraints only. It is not a
substitute for reviewing the [`docs/customer-managed-infrastructure.md`](./customer-managed-infrastructure.md)
pre-release upgrade boundary, which covers Terraform-state-shape changes
(for example the `modules/controllers` composition) separately from the
Azure-resource constraints above.
